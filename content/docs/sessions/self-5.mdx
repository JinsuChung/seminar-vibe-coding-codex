## 1일차 SQL 네 문장만 읽자

<KeyPoints
  items={[
    'DB가 붙으면 "보여 주는 페이지"가 "일하는 앱"이 된다.',
    '키는 환경변수, 비밀 키는 서버에서만, RLS는 반드시.',
    'AI에게 만들게 했으면 보안 점검도 AI에게 시킨다. 판단은 사람이.',
  ]}
/>

SQL은 직접 쓸 필요가 없습니다. 하지만 AI가 만든 SQL을 **읽고 이상한 점을 알아채는 눈**은 필요합니다. 네 가지만 알면 대부분 읽힙니다.

<DeepDive title="엑셀 동작으로 읽는 SQL">

| SQL | 엑셀로 치면 | 예 |
| --- | --- | --- |
| `select … from requests` | 시트에서 보고 싶은 열만 보기 | `select title, due_date from requests` |
| `where …` | 필터 | `where due_date < '2026-11-01'` |
| `order by …` | 정렬 | `order by due_date` |
| `insert into requests …` | 맨 아래 새 줄 추가 | `insert into requests (title, due_date) values ('새 요청', '2026-12-01')` |
| `update requests set … where …` | 조건에 맞는 칸 고치기 | `update requests set owner = '김담당' where id = 3` |
| `delete from requests where …` | 조건에 맞는 줄 삭제 | `delete from requests where id = 3` |

<Callout type="warn" title="이 두 줄은 꼭 다시 보기">
  `where` 없는 `update`와 `delete`는 **모든 행**을 바꾸거나 지웁니다. AI가 만든 SQL에 `where`가 없는 `update`·`delete`가 있으면 실행하지 말고 물어보세요.
</Callout>

</DeepDive>

## 2일차 RLS를 직접 시험한다

<DeepDive title="정책 네 개를 표로 읽기">

5회차 완성본의 `schema.sql`에는 정책이 네 개 있습니다.

| 정책 | 누가 | 무엇을 | 조건 |
| --- | --- | --- | --- |
| 누구나 읽기 | 방문자·로그인 사용자 | 보기 (select) | 항상 |
| 로그인한 직원만 추가 | 로그인 사용자 | 추가 (insert) | 항상 |
| 등록한 본인만 수정 | 로그인 사용자 | 고치기 (update) | `created_by = auth.uid()` (내가 등록한 것) |
| 등록한 본인만 삭제 | 로그인 사용자 | 지우기 (delete) | 내가 등록한 것 |

`auth.uid()`는 "지금 로그인한 사람의 번호"입니다. 그래서 **남이 등록한 요청은 고치거나 지울 수 없습니다.**

</DeepDive>

<Lab session={5.5} title="미션 2 · 두 계정으로 권한 시험" level="필수" minutes={20} goal="화면에서 막히는 것과, 데이터베이스에서 막히는 것을 모두 확인합니다.">
<Step id="m2-1" title="담당자 계정 하나 더 만들기">
<p>Supabase 대시보드 <b>Authentication → Users → Add user → Create new user</b>로 두 번째 계정(예: <code>tester2@example.com</code>)을 만들고 <b>Auto Confirm User</b>를 켭니다. 비밀번호는 본인이 정해 직접 입력하세요.</p>
</Step>
<Step id="m2-2" title="계정 A로 요청 1건 등록">
<p>localhost에서 첫 번째 계정으로 로그인해 업무 요청을 하나 등록합니다.</p>
</Step>
<Step id="m2-3" title="계정 B로 지워 보기">
<p>로그아웃 → 두 번째 계정으로 로그인 → 방금 등록한 요청의 <b>삭제</b>를 눌러 봅니다.</p>
<Expected>{`
⚠ 본인이 등록한 요청만 삭제할 수 있어요 (RLS 정책).
`}</Expected>
<p>그다음 두 번째 계정으로 요청을 하나 등록하고 지워 보세요. 내 것은 지워집니다.</p>
</Step>
<Step id="m2-4" title="로그아웃 상태에서 확인">
<p>로그아웃하면 목록은 보이지만 등록 폼과 삭제 버튼이 사라집니다. 화면에서 버튼을 숨긴 것과 별개로, <b>데이터베이스도 막고 있다</b>는 것을 Codex에 확인해 보세요.</p>
<PromptCard title="정말 막혀 있는지" text="로그인하지 않은 사용자가 화면을 거치지 않고 공개 키로 직접 requests에 insert나 delete를 시도하면 어떻게 되는지, schema.sql의 정책을 근거로 설명해줘." compact />
</Step>
</Lab>

## 3일차 항목 하나 추가하기

<Lab session={5.5} title="미션 3 · 지원 규모 항목 추가" level="필수" minutes={25} goal="데이터베이스 → 화면 → 설계 파일까지 세 곳을 함께 바꾸는 연습입니다.">
<Step id="m3-1" title="계획 먼저">
<PromptCard
  title="항목 추가 계획"
  text="업무 요청에 '긴급도'(낮음/보통/높음) 항목을 추가하려고 해. 아직 실행하지 말고, Supabase에서 실행할 SQL, 화면에서 바꿀 곳(목록 카드, 등록 폼), supabase/schema.sql 수정 내용을 계획으로 보여줘."
/>
<Expected>{`
● 계획
  1) SQL Editor에서 실행: alter table public.requests add column priority text;
  2) components/board.tsx — 카드에 긴급도 표시, 등록 폼에 선택 칸 추가
  3) supabase/schema.sql — create table에 priority 컬럼과 값 제한 추가
  RLS 정책은 바꿀 필요 없음 (행 단위 규칙이라 새 컬럼에도 그대로 적용)
`}</Expected>
</Step>
<Step id="m3-2" title="SQL 실행하고 화면 바꾸기">
<p>계획의 SQL을 Supabase <b>SQL Editor</b>에 붙여 넣고 <b>Run</b>. 그다음 승인해서 화면과 schema.sql을 고치게 합니다.</p>
</Step>
<Step id="m3-3" title="확인하고 커밋·배포">
<p>localhost에서 긴급도를 넣어 등록해 보고, Table Editor에 값이 들어갔는지 확인한 뒤 커밋·푸시하세요.</p>
<Trouble>
<Issue q="column does not exist 에러가 나요">SQL을 아직 실행하지 않았거나 다른 프로젝트에서 실행한 경우입니다. 대시보드 왼쪽 위 프로젝트 이름이 맞는지 확인하고 다시 실행하세요.</Issue>
</Trouble>
</Step>
